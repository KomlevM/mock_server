### 2.5 Тэги

- Все уникальные значения из данных, ничего не менял.
- Регистр сохраняю: `iOS` и `ios` — разные теги (в данных это разные значения).
- Пустой массив `[]`, не `null` и не `"Неизвестно"`. Фронт рисует `"-"`.
- Фильтр по тегу — вхождение в массив (строка или массив = OR).

### 2.6 `UNKNOWN` / `NULL`

- **`UNKNOWN`** (`"Неизвестно"`) — значение непустое, но не прошло алиасы/справочники. Для `status`, `priority`, `project`, `assignee`, дат, `estimate`.
- **`NULL`** (`null`) — значение пустое (`null`, `""`, `" "`, маркеры «не назначено»).
- Для `title`, `description`, `source`, `key` — только `null`, без `"Неизвестно"` (текст, «неизвестно» не имеет смысла).
- **`id` для фильтров**: `NULL = -1`, `UNKNOWN = 0`.
- Бэк принимает `-1`/`0` в фильтрах и мапит: `-1` → `null` («без исполнителя/проекта»), `0` → `"Неизвестно"`.
- Фронт различает: `"Неизвестно"` — бейдж/серый, `null` — `"-"`.
- Фильтр `{"status": "Неизвестно"}` находит все нераспознанные; `{"assignee": -1}` — без исполнителя; `{"assignee": 0}` — нераспознанные.

### 2.7 Даты

- 4 вида (`created`, `due`, `updated`, `completed`) × 4 варианта написания (`*_date`, `*_local`, `*_utc`, `*_ts`).
- `parse_dt` понимает: ISO с `Z` (`2026-02-17T18:36:00Z`), ISO с offset (`+03:00`), unix-секунды (`1758308640`), unix-миллисекунды (`1760794620000`, `>1e12` → /1000), `dd.mm.yyyy hh:mm`.
- На бэке — UTC (aware `datetime`), на фронт — `dd.mm.yyyy HH:mm` (UTC). Почему UTC: можно наглядно тестировать и конвертировать.
- **Приоритет полей** для `TaskDto.due`: `due` → `due_date` → `due_utc` → `due_ts` → `due_local`. `due` — самое «чистое», `due_local` — последнее (без зоны).
- **`due_local` без зоны** считаю UTC: `strptime(...).replace(tzinfo=utc)`.
- **Противоречия**: в `all_data` — все сырые поля, открываются в модальном окне.
- **`due < created`** — бейдж «срок раньше создания» на карточке и в ленте. Не маскирую.
- Пустое → `null`; непустое непарсимое → `"Неизвестно"`.

### 2.8 `estimate`

- Форматы: `2`, `2.0`, `"2h"`, `"8h"`, `"3,5"`, `"3.5"`, `"4 часа"`, `"1d"`, `"0.5d"`, `"0.5"`, `"?"`, `""`, `null`.
- Парсер: число + единица; запятая → точка; `d/д/день/дня/дней` → ×8 (1д = 8ч, стандарт трекеров); `h/ч/час/часа/часов` → ×1; без единицы → ×1 (часы).
- `"?"` → `"Неизвестно"`, `""`/`null` → `null`.
- Сортировка по `estimate`: `null`/`"Неизвестно"` — в конец (при `asc` и `desc`).

### 2.9 Комментарии

- Источник — `comments.json`. Комментарии тоже грязные: кракозябры (UTF-8, прочитанный как CP1252/latin-1: `ÐŸÑ€Ð¸Ð²ÐµÑ‚` → `Привет`), пустые поля, `created` в разных форматах.
- **`_fix_mojibake`**: проходит по строке, для каждого символа, который есть в CP1252-таблице (`_CP1252_TO_BYTE`), берёт соответствующий байт; иначе кодирует в latin-1; затем всё это декодирует как UTF-8. Если не получилось (не UTF-8 после сборки) — возвращает исходную строку (не портит данные).
- Применяется к текстовым полям комментария (`text`, `author`), не к `id`/`created`.
- `created` — через тот же `parse_dt`, что и задачи (ISO / unix сек / unix мс / `dd.mm.yyyy`), на выходе `dd.mm.yyyy HH:mm`.
- Пустые поля → `null`, нераспознанные даты → `"Неизвестно"` (как в `TaskDto`).
- **Почему на бэке, а не на фронте**: кракозябры — проблема данных, а не отображения; если чинить на фронте, каждый клиент (мобилка, экспорт) повторяет логику. `_fix_mojibake` — часть `normalization.py`, тесты — `test_mojibake.py`.
- **XSS**: Не трогал тк, экранирование — на фронте (Angular `{{ }}`).

### 3.3 Сроки

- **Просрочено**: `due < now` (строго; `due == now` — «истекает сейчас», не просрочено).
- **Скоро N дней**: `now <= due <= now + N*24h` (N задаёт пользователь, `N >= 0`; `N = 0` — «истекает сегодня»).
- **Без срока**: `due is None`.
- **Срок битый**: `due == "Неизвестно"` — отдельно («срок неизвестен»), не путать с «без срока».
- **Противоречия**: `due < created` — бейдж; `due` vs `due_utc`/`due_ts`/`due_local` расходятся — на карточке все сырые.
- Срочность: цвет (красный — просрочено, жёлтый — скоро, серый — без срока) + сортировка по `due`.

### 3.4 Модальное окно

### 3.7 Heartbeat

### 3.8 Сводка к стендапу

`POST /api/v2/summary` — счётчики по отфильтрованным. Правила:
- **Просрочено**: `due < now`, `due` не `null`/`"Неизвестно"`.
- **Неизвестные данные** (доп.): `status == "Неизвестно"` или `priority == "Неизвестно"` или `project == "Неизвестно"` или `assignee == "Неизвестно"` — сколько задач с хоть одним `UNKNOWN`. Сигнал о качестве данных, не бизнес-метрика.
- **Без срока**: `due is None`.
- **Срок раньше создания**: `due < created` (оба не `null`).
- **С дедлайном в N дней**: `now <= due <= now + N*24h`.

- **Заблокировано**: `status == "BLOCKED"` - можно получить через фильтры + счетчик всего записей, тк добавил статус `"Заблокирована"`.
- **Без исполнителя**: `assignee is None` - можно получить через фильтр `"Нет исполнителя"` + счетчик всего записей.

## 4. Мониторинг

### 4.1 Метрики

- **Uptime** (время с запуска): сколько сервис работает без рестарта. Зачем: маленький uptime — сервис падает и рестартует; в 3 часа ночи видно, что «только что поднялся».
- **Latency p95**: 95-й перцентиль времени ответа. Зачем: среднее врёт (один медленный запрос тонет в быстрых), p95 показывает «как чувствуют себя 95% пользователей». Растёт — API захлёбывается.
- **5xx rate**: доля ответов 5xx от всех. Зачем: 5xx — ошибки сервера (баг, падение, таймаут). > 0 — что-то сломалось. 4xx (429, 400) — ошибки клиента, не «сервер лежит».
- **RPS** (requests per second): запросов в секунду. Зачем: базовая нагрузка; RPS → 0 — клиенты ушли или сервер не принимает; RPS растёт с p95 — перегрузка.
- **`http_requests_total{status}`** — счётчики по кодам (200, 4xx, 5xx).
- **`rate_limit_hits_total`** — сколько 429. Много — клиент долбит или лимит низкий.
- **`normalization_errors_total{field}`** — сколько раз поле не распозналось. «Качество данных», часть задания.
- **`last_successful_response_timestamp`** — когда последний успешный ответ. В 3 часа ночи — видеть, что API отвечает, а не просто «uptime 5 дней».

Почему p95, а не среднее: среднее маскирует хвост. Почему 5xx, а не 4xx: 4xx — клиент. RPS — базовая нагрузка. Uptime — рестарты.

### 4.2 Эндпоинт

- `GET /api/v2/metrics` — Prometheus text (version=0.0.4).
- `GET /api/v2/metrics/json` — JSON для виджета.

### 4.3 Виджет

- Состояние API (health/pulse) + график латентности (p95) + счётчик ошибок (5xx) + 429 + «когда последний успешный ответ».
- «Что открыл бы в 3 часа ночи»: p95, 5xx rate, 429, last_success и логи

### 4.4 Внешние инструменты

Не тащил. Причины:
- один сервис, mock-нагрузка - Prometheus + Grafana + экспортёр = 3 контейнера  ради того, что уже отдаёт `/metrics`.
- свой виджет на доске закрывает: p95, 5xx rate, 429, last_success — без внешней инфраструктуры.
- `/metrics` в формате Prometheus — если завтра понадобится Grafana, подключится без правок бэка (endpoint уже совместим).

## 9. Как шла работа

Работа заняла порядка **32 часов**. Порядок был таким:

1. **Начал с фронта** — чтобы визуализировать данные и понять, что вообще приходит. Сначала сделал нормализацию **на фронте** (статусы, приоритеты, даты — в TypeScript-сервисах). По ходу понял, что это неправильно: нормализация на клиенте — дублирование, фронт зависит от грязных данных, и любой новый клиент (мобилка, экспорт) должен повторять ту же логику. Перенёс нормализацию на бэк (`normalization.py`), фронт стал тоньше. Это решение считаю правильным, но оно стоило переделки.
2. **Метрики** — на старте не знал, что это такое и как их снимать. Разобрался по ходу: счётчики, гистограмма латентности, p95, 5xx rate. Сделал `metrics.py` + `/metrics` + виджет на доске. Понял, что «мониторинг» — это не «Prometheus поставил», а «знаю, что открою в 3 часа ночи».
3. **Деплой** — не делал раньше nginx, не работал с серверами на чистом Python, с бэком на Python давно не связывался. По ходу: systemd, nginx reverse proxy, статика, SSH по ключу, `Permission denied (publickey)`, `Address already in use`, nano не сохранил конфиг. Всё это — в п.5 «что всплыло на VPS».

**Что можно было сделать качественнее:**

- Из-за постоянных переделок логики (что оставить в фильтрах, что вынести на панельки, где показывать сводку) потратил много времени впустую. Не было чёткого представления итогового результата, пока не разобрался с панельками — а это уже середина работы. Если бы сначала нарисовал макет/схему экранов, переделок было бы меньше.
- Фронт из-за этого усложнился: часть логики переехала на бэк, но интерфейсные решения (какие фильтры в панели, какие в шапке, где сводка) менялись несколько раз. В итоге код на фронте сложнее, чем мог бы быть при более раннем понимании UX.
- Нормализация на фронте в начале — тоже переделка. Если бы сразу понял, что источник правды — бэк, сэкономил бы время.

**Что помогло:**

- Нейронка и опыт работы дизайном разного рода фильтров, разной сложности + насмотренность на грязные данные. 
- Желание заставить это работать, с метриками и на VPS.
